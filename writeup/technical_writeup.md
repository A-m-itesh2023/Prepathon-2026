# AI Agent for Kubernetes Root-Cause Analysis

**Amitesh Mitra · 26055002 · Industrial Chemistry · IIT (BHU)**

## Problem framing
The problem statement requires an AI agent that investigates Kubernetes incidents rather than merely summarising logs. It must gather evidence iteratively, form and update hypotheses, distinguish symptoms from underlying causes, operate inside a controlled sandbox, and provide reproducible incidents with known ground truth.

## Architecture
The prototype maintains explicit investigation state: incident, evidence ledger, competing hypotheses, query history, causal timeline and uncertainty. A read-only gateway exposes Kubernetes resources, Events and container logs; Prometheus is an additional metrics source. The reasoner selects the next evidence source from current evidence gaps instead of blindly executing a fixed sequence.

## Observability
Configured sources are Kubernetes API resources, Kubernetes Events, application/container logs and Prometheus metrics. Loki/Grafana/Elasticsearch/Jaeger/Tempo are extension points rather than silently claimed implementations.

## Investigation
The investigation loop is:
1. Parse the incident.
2. Establish initial Kubernetes observations.
3. Create competing hypotheses.
4. Select the next evidence source.
5. Retrieve evidence through the read-only gateway.
6. Update hypothesis support.
7. Construct a timeline.
8. Stop when evidence is sufficient or report insufficient confidence.
9. Produce a structured RCA.

## Reproducible scenarios
Four scenario families are included:
- OOM/resource exhaustion.
- Bad deployment.
- Dependency failure, which requires correlating API/dependency evidence.
- Configuration drift.

Each scenario has an explicit ground-truth failure mode.

## Security
The sandbox is enforced through capability restriction. There is no generic shell/exec operation, no Secret retrieval, no host access and no cluster-admin mutation. Retrieved observability text is untrusted data. A prompt-injection string inside a log therefore remains evidence and cannot become a tool instruction.

## Evaluation
Evaluation should compare the RCA root cause against scenario ground truth and inspect whether the cited evidence supports the causal chain. Additional checks cover evidence coverage, investigation depth, multi-source use, unsupported claims and security-boundary violations.

## Limitations
This is a local prototype rather than a production monitoring platform. Tracing and richer change-history correlation remain extension points. Quantitative benchmark results are intentionally not fabricated; they should be generated by running the reproducible environment.

## Next steps
Add an explicit causal graph, tracing integration, historical incident retrieval, richer deployment/configuration diffs, and an LLM planner constrained by the same read-only gateway.
